# 已確認的正式程式缺陷與回歸案例

## Q-001 — 四份同種字牌不能重複當作未來可擴充的搭子（高）

最小可重現（在目前 `shanten` API 的合法張數限制下）：

```js
const hand16 = [27,27,27,27, 28,28,28,28, 29,29,29,29, 30,30,30,30];
shanten(hand16); // 正式程式目前返回 2；獨立 Oracle 與物理牌數限制推得 4。
```

推導：目前只有東南西北四組各四張；一般五面子一將眼至少需要額外第五組面子與一組將眼。由於每種牌最多四張，同組字牌不能同時用三張刻子又取兩張作將眼，從現有手牌最多保留 12 張（四組刻子）。最終 17 張完整目標至少需加入 5 張不同於原手牌的牌，因此還需替換 4 張並額外摸 1 張；向聽 `16 - 12 = 4`。正式 DFS 將同種四張拆為虛假「對子／搭子」資源，低估需求。`tests/golden-shanten.test.js` 以 TODO 失敗斷言保留，預期值固定為 4。

**建議修法（不屬本分支）**：由核心演算法工程師修正四份牌的組合可達性判斷，並重新跑 Golden/10k+ oracle；不得把 golden 改為 2 來過關。

## Q-002 — 當前被打出的牌仍被計為可摸進張（中）

```js
const hand17 = [0,0,0,0,1,2,9,10,11,18,19,20,27,27,27,28,28];
const ranked = rankDiscards(hand17);
const candidate = ranked.find(x => x.tile === 0);
// candidate.copies === 7（其中 1 張 1萬 是剛捨棄的那張）
const after = [...hand17]; after.splice(after.indexOf(0), 1);
improvingDraws(after, [0]).copies; // 6（已知剛捨出的 1萬不可再在牆內）
```

目前 `rankDiscards` 在移除候選捨牌後直接以餘下 16 張計算；未把被捨牌納入已知可見牌，所以候選捨牌恰好為潛在有效進張時會憑空多算一張。題目無明牌時也受影響，可能改變同向聽數下的排名與評級。`tests/golden-scoring.test.js` 以 TODO 斷言保留真正剩餘數 6。

**建議修法（不屬本分支）**：由題庫工程師在每種候選捨牌計算進張時，將該捨牌作為額外已知不可摸牌，再與原 `visible` 合併並防止雙重扣除。
